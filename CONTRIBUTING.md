# Contributing

Thanks for looking. This is a small plugin with a narrow scope, and most of what follows exists to keep it that way.

## Before you open a pull request

Read the **Design decisions** section of [README.md](README.md). These are load-bearing, and a change that breaks one will be declined regardless of how well it is written:

1. **The saved markup stays a plain span** with a class and a data attribute. Nothing that would need a KSES exception, and nothing that would invalidate a block once the plugin is gone.
2. **Text goes in with `textContent`.** The words are never parsed as HTML.
3. **The original word is what assistive technology gets**, and nothing moves under `prefers-reduced-motion: reduce`.
4. **The front-end assets load only where the format is used**, from `render_block`.
5. **The toolchain is `@wordpress/scripts` and nothing else.** The `@wordpress/*` packages are devDependencies, externalised by webpack to the `wp.*` globals; nothing from `node_modules` ships.
6. **No runtime Composer dependency.** `composer.json` exists for PHPCS and PHPUnit and is excluded from the release.

Also declined by default: a settings page, an option in the database, an admin notice, a credit in the front-end output, an outgoing request of any kind, and a bundled copy of a library WordPress already ships.

## Setting up

```bash
git clone git@github.com:Fyrins/retype.git
cd retype
composer install
npm install
npm run build
```

`npm run build` is not optional: `build/` is not in the repository. Use `npm start` while working on `src/`; it rebuilds on save.

A disposable WordPress in a directory of its own is enough, with the plugin synced in through `.distignore`, so you are looking at what ships:

```bash
rsync -a --delete --delete-excluded --exclude-from=.distignore \
  /path/to/retype/ /path/to/wordpress/wp-content/plugins/retype/
```

`--delete-excluded` is not optional. Without it rsync protects excluded files from deletion, and the target stays polluted by whatever the previous sync left there.

## What has to pass

### JavaScript and styles

```bash
npm run lint:js
npm run lint:style
npm run test:js
npm run build
```

Nothing reported. `.prettierrc.js` re-exports `@wordpress/prettier-config`; without it `format` and `lint-js` would reformat the same file two different ways.

### PHPCS

```bash
composer lint
```

Nothing reported, warnings included. The ruleset is `phpcs.xml.dist`: WordPress plus PHPCompatibilityWP, `testVersion` 7.4 and up, `minimum_wp_version` 6.6.

### PHPUnit

The tests run against a real WordPress with `wp-phpunit/wp-phpunit`, not against mocks. They need a WordPress install, a database the test library is allowed to **empty**, and a build:

```bash
npm run build
export WP_CORE_DIR=/path/to/wordpress           # any WordPress 6.6 or later
export WP_TESTS_DB_HOST=127.0.0.1:3306
export WP_TESTS_DB_NAME=retype_tests            # never a site's database
export WP_TESTS_DB_USER=root
export WP_TESTS_DB_PASSWORD=root
composer test
```

With a DDEV testbed, create the database once and use the published port:

```bash
ddev mysql -uroot -proot -e "CREATE DATABASE IF NOT EXISTS retype_tests"
export WP_TESTS_DB_HOST=127.0.0.1:$(ddev describe -j | jq -r '.raw.dbinfo.published_port')
```

CI does the same with a `mysql:8.0` service and `wp core download --version=latest`.

A test written for a fix has to fail without the fix. Put the defect back for one run and check that the new test is the one that fails.

### Plugin Check

On the built package, in a directory named exactly `retype`, across all five categories:

```bash
npm run build
rsync -a --delete --delete-excluded --exclude-from=.distignore ./ dist/retype/
# with the package synced into a WordPress that has the plugin-check plugin active:
wp plugin check retype \
  --categories=general,plugin_repo,security,performance,accessibility \
  --include-experimental
```

Zero errors, zero warnings. On the source tree it reports the development files; under another directory name it infers the wrong text domain.

### Manual verification

With `WP_DEBUG` and `WP_DEBUG_LOG` on, front end and editor, in English and in a translated locale, `debug.log` has to stay empty. Prove the log works first by triggering a notice on purpose, otherwise an empty log proves nothing. Then check, on a page that uses the format:

- the script and the stylesheet are on that page and not on a page without the format;
- the heading's accessible name is the original sentence while the word animates;
- with reduced motion emulated, the original word stays and nothing blinks;
- the text after the word follows it as it is typed and erased, and the word never breaks across two lines;
- with the plugin deactivated, every block that used the format is still valid in the editor.

## Translations

`languages/retype.pot` is regenerated by `npm run i18n` from the built package files, and is the only file shipped in `languages/`.

`translations/retype-fr_FR.po` is the French translation, kept outside the package for import on translate.wordpress.org after approval. When strings change, merge it with the new template (`msgmerge --update translations/retype-fr_FR.po languages/retype.pot`) and translate the new entries. To try it locally, compile it into the test site, never into the repository:

```bash
cp translations/retype-fr_FR.po /path/to/wordpress/wp-content/languages/plugins/
wp i18n make-mo /path/to/wordpress/wp-content/languages/plugins/
wp i18n make-json /path/to/wordpress/wp-content/languages/plugins/retype-fr_FR.po --no-purge
```

## Releasing

1. Bump the version in `retype.php` (header and `RETYPE_VERSION`), the readme `Stable tag`, `package.json` (`npm version --no-git-tag-version`), and add the sections to `CHANGELOG.md` and to the readme changelog. `scripts/check-versions.sh` checks all of it.
2. Merge to `main`.
3. Tag `vX.Y.Z` on `main` and push the tag. `deploy.yml` runs the whole CI suite, refuses a tag that is not on `main`, checks the versions, builds, publishes to the SVN repository, then creates the GitHub release from the changelog.

Publishing goes through the `wordpress-org` GitHub environment, which requires an approval in the Actions tab and only accepts `v*` tags. `SVN_USERNAME` and `SVN_PASSWORD` live in that environment, and only the maintainer sets them.
